Decode context parallelism, from the attention math up

Every serving trick in the scaling part of the talk comes down to one question: which axis of which tensor gets split across GPUs. This page builds that up in seven steps. Each step has a figure you can change.

Tensor parallelismsplits headsWeights and the KV cache are cut along the attention-head axis.
MLA modelshave one shared KV vectorThere is no KV-head axis left to cut, so every GPU keeps the same cache.
Decode context parallelismsplits tokensThe cache is cut along the sequence instead, and partial results are merged exactly.
1

Attention for one new token

While generating, each step produces one new token. That token's query q is scored against the key k of every earlier token. The scores go through a softmax, and the output is the softmax-weighted average of the earlier tokens' values v. The K and V of every earlier token are what the KV cache stores, so they are not recomputed each step.

Drag the scores. Each token's weight is e^score / Σ e^score; the output is Σ weight · v. The values v are scalars here to keep the arithmetic visible; in a real model each is a vector of 128 or 512 numbers.

One output needs every cached token. Remember this for step 6: if the tokens live on different GPUs, the softmax has to be split and put back together.

2

What one token costs in the cache

Every layer caches something for every token. How much depends on the attention design. With full multi-head attention, each of the 32 heads has its own K and V. With grouped-query attention (GQA), 32 query heads share 8 KV heads. With multi-head latent attention (MLA), K and V are compressed into one shared vector that every head reads.

Numbers cached per token, per layer. MHA and GQA use Llama-3-8B-sized heads (head_dim 128, K and V both cached). MLA uses GLM-5.3's config: a 512-wide latent plus a 64-wide position key, 576 in all.

MLA's cache is 3.6× smaller per token than this GQA layer, and 14× smaller than full multi-head attention. Hold that thought: step 3 shows how tensor parallelism throws much of that saving away.

3

Tensor parallelism is a split matrix multiply

Tensor parallelism (TP) cuts the attention layer's weight matrices across GPUs, called ranks. W_Q, W_K and W_V are cut by output columns, which here means by head. Each rank computes Q, K and V only for its own heads, runs attention for those heads with no communication, and one all-reduce sums the partial outputs at the end. A rank only ever computes K and V for its own KV heads, so that is all it caches.

Tensor-parallel size

GQA's cache per rank shrinks as you add GPUs, until there are more GPUs than KV heads. MLA's never shrinks: its K and V come from one down-projection (W_DKV) with no head axis, so every rank computes and stores the same 576 numbers per token.

4

How MLA attends without K and V

In MLA, each head would rebuild its own key from the shared latent c_j with an up-projection, k = c_j · W_UK. Because the score is a dot product, that up-projection can be moved onto the query once per step instead of onto every cached token. This is called absorption. Attention then runs directly against the cached latents.

score_j = q · k_j = q · (c_j W_UK)ᵀ = (q W_UKᵀ) · c_j = q̃ · c_j
output = (Σ_j weight_j · c_j) · W_UV

Position needs one extra piece. Rotary position encoding cannot be absorbed this way, so MLA adds a small 64-wide position key per token, shared by all heads. That is the "+ 64" in 576.

At decode time an MLA layer behaves like attention with a single 576-wide KV head that all 64 query heads read. One head is the worst case for tensor parallelism: there is nothing to split.

5

Decode context parallelism splits the tokens

Decode context parallelism (DCP) keeps the 576-wide latent whole and splits the other axis: token t is stored on rank t mod D. It reuses the same GPUs as tensor parallelism. Each rank now holds every head's share of a quarter of the tokens, instead of all tokens for a quarter of the heads.

DCP size

The cache per rank falls by the DCP size, so the same GPUs hold that many times more tokens. On GLM-5.3 with 8 × B200, going from DCP 1 to DCP 8 grew the GPU KV pool from 2.0M to 15.4M tokens.

6

The key idea: softmax can be split and merged exactly

Now no rank has all the tokens. Each rank runs the softmax over only its own tokens and returns two things: its partial output o_r, and Z_r, the sum of e^score over its tokens. Weighting each partial by its share of the total, Z_r / Z, and adding them gives exactly the full answer. It uses the scores from step 1 and the DCP size from step 5.

RankIts tokensZ_r = Σ e^scoreo_r (local softmax)Weight Z_r / ZWeight × o_r

In practice each rank sends log Z_r (the log-sum-exp, or LSE) instead of Z_r, so large scores cannot overflow. The weights become exp(LSE_r − LSE): the same numbers, computed safely. This is the identity behind FlashAttention's online softmax and Flash-Decoding, applied across GPUs instead of across chunks on one GPU.

Nothing is approximated. The only extra data per head is one partial output and one number per rank.

7

The price: two exchanges on every decode step

Tensor parallelism gave each rank only its own heads' queries, but under DCP each rank must attend with every head over its tokens. So every attention layer, on every decode step, gains two collectives: an all-gather of the queries, then the merge of partial outputs and LSEs back to each rank's own heads. Their size does not depend on context length. The cache they save does.

Estimate for GLM-5.3, 78 layers, TP = DCP = 4, one sequence, FP8 cache (1 byte per number) and 16-bit messages. Exchanged per rank per layer: about 55 KB for the query all-gather plus about 49 KB for the merge, so about 8 MB per decode token across all layers. Real cost depends on the interconnect and batch size.

DCP pays when the cache is what runs out: long agent contexts, many concurrent sessions. It costs per-token latency when contexts are short and speed per user matters most. Measured on one 8 × B200 node at 24 sessions, one replica with DCP gave 34 tokens/s per user against 50 for two smaller replicas without it, a layout comparison rather than DCP alone.

Check yourself

Does DCP split the query matrix?

No. Tensor parallelism already splits W_Q by head. DCP partly undoes that split at attention time: each rank gathers the queries for all heads, because it holds a slice of every sequence's tokens.

Why doesn't TP shrink MLA's cache?

TP cuts along heads. MLA's cache is one shared latent per token, produced by a down-projection with no head axis, so every rank needs all of it.

Is the merge approximate?

No. Softmax over all tokens equals the weighted sum of per-rank softmaxes, with weights Z_r / Z. The LSE form only changes how the weights are computed, for numerical safety.

When would you leave DCP off?

When contexts are short or few sessions run at once, so the cache is not the limit. The two extra exchanges then only add latency to every token.
